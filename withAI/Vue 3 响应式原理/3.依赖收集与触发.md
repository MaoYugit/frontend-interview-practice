## 设计依赖管理的核心数据结构

在手写 Vue 3 响应式的第三阶段，我们将设计整个系统中最关键的数据结构。这套结构被形象地称为 **“依赖关系树”**。

它负责在内存中记录：**哪个对象**的**哪个属性**被**哪些副作用函数（effect）**依赖了。

Vue 3 采用了一种精心设计的嵌套结构：`targetMap (WeakMap) -> depsMap (Map) -> dep (Set)` [1.1.2]。理解这个结构的设计原因，能帮你掌握 Vue 3 底层性能优化的精髓。

---

### 一、 核心数据结构关系图

在脑海中，你可以把这个依赖结构想象成一棵三层的树：

```text
targetMap (WeakMap)
 └── key: target (目标对象，如 { name: 'Vue 3', count: 1 })
      └── value: depsMap (Map)
                  ├── key: "name" (具体属性名)
                  │     └── value: dep (Set) ──> [ effectFn1, effectFn2 ] (副作用函数列表)
                  │
                  └── key: "count" (另一个属性名)
                        └── value: dep (Set) ──> [ effectFn1 ]
```

#### 概念对应关系：
1.  **第一层 `targetMap`**：管理**所有代理对象**。通过“对象本身”作为 Key，找到它对应的所有属性依赖。
2.  **第二层 `depsMap`**：管理**某个对象的所有属性**。通过“属性名（Key）”作为 Key，找到该属性对应的副作用函数集合。
3.  **第三层 `dep`**：一个具体的**副作用函数集合（Set）**。存放所有依赖该属性的 `effect` 包装函数。

---

### 二、 为什么选择这三种数据类型？（精妙的设计考量）

这是面试中非常核心的理论考点，也是手写前必须厘清的逻辑：

#### 1. 为什么 `targetMap` 必须使用 `WeakMap`？
*   **防止内存泄漏**：`WeakMap` 的键（Key）只能是对象，并且是**弱引用**。
*   **原理**：如果一个目标对象 `target` 在业务代码中已经没有任何地方引用它了（比如组件销毁、变量置空），垃圾回收机制（GC）就会自动将它回收。
*   *如果使用普通 `Map`*，`Map` 对 `target` 的引用是强引用，即使业务代码中销毁了该对象，`Map` 依然拉着它，导致它无法被回收，从而产生内存泄漏。
*   *使用 `WeakMap`*，一旦外部没有引用 `target`，垃圾回收机制会自动把 `target` 及其在 `targetMap` 中对应的 `depsMap` 一起清理掉 [1.1.2]。

#### 2. 为什么 `depsMap` 使用普通的 `Map`？
*   因为属性名（如 `"count"`、`"name"`）通常是字符串（String）或 `Symbol` [1.1.2]。
*   `WeakMap` 的 Key 只能是对象，不能是字符串。而普通的 `Map` 允许使用字符串作为 Key，完全满足属性匹配的需求。

#### 3. 为什么 `dep` 集合使用 `Set`？
*   **防止重复收集**：同一个 `effect` 内部如果多次读取了同一个响应式属性，例如：
    ```javascript
    effect(() => {
      console.log(state.count);
      console.log(state.count); // 读取了两次
    });
    ```
*   如果不去重，这个 `effect` 会在依赖列表中存两份，数据改变时就会被重复触发执行。`Set` 的天生去重特性（元素唯一性）优雅地解决了这个问题 [1.1.2]。

---

### 三、 依赖结构的初始化代码实现

在正式写 `track`（依赖收集）和 `trigger`（触发更新）之前，我们需要在全局定义并学会如何安全地“检索与创建”这套三层结构。

我们在一个新的 `reactive.js`（或单独的依赖管理文件）中定义它：

```javascript
// 1. 全局依赖图表
// key: target (Object) -> value: depsMap (Map)
export const targetMap = new WeakMap();

/**
 * 辅助函数：安全地获取或创建指定对象属性的 dep 集合
 * 这个逻辑在 track 和 trigger 中都会被频繁使用
 */
export function getDepSet(target, key) {
  // 1. 从 targetMap 中获取该对象的 depsMap
  let depsMap = targetMap.get(target);
  
  // 2. 如果不存在，说明是第一次访问该对象，初始化一个空的 Map 并存入 targetMap
  if (!depsMap) {
    depsMap = new Map();
    targetMap.set(target, depsMap);
  }

  // 3. 从 depsMap 中获取该属性对应的 dep (Set)
  let dep = depsMap.get(key);
  
  // 4. 如果不存在，说明该属性第一次被读取，初始化一个空的 Set 并存入 depsMap
  if (!dep) {
    dep = new Set();
    depsMap.set(key, dep);
  }

  // 5. 返回对应的 Set 集合，此时可以安全地进行 add(effect) 或 遍历执行
  return dep;
}
```

这就是 Vue 3 依赖管理的核心底座。有了这一套设计，我们现在万事俱备。

## 实现 track 函数

在第三阶段的第二部分，我们来编写最核心的 **`track`（依赖收集）** 函数。

`track` 的使命是：当我们在 `effect` 中读取某个响应式属性时（触发 Proxy 的 `get`），自动将当前活动的副作用函数 `activeEffect` 记录到该属性对应的 `dep`（Set）中。

为了保证后续阶段（如“分支切换与依赖清理”）能够顺利进行，我们在收集依赖时不仅要把 `activeEffect` 存入 `dep`，还要让 `activeEffect` 反向记录一下自己被存到了哪个 `dep` 里（建立**双向收集**关系）[1]。

---

### 1. 实现 `track` 函数

我们在 `effect.js`（或单独的 `effect.js` / `reactive.js` 统一文件中）实现 `track`：

```javascript
import { activeEffect } from './effect.js';

// 全局依赖图表（上一节定义的 targetMap）
export const targetMap = new WeakMap();

/**
 * 收集依赖
 * @param {Object} target 原始目标对象
 * @param {string|symbol} key 被读取的属性名
 */
export function track(target, key) {
  // 1. 如果当前没有处于运行状态的 activeEffect，说明该读取操作不发生在 effect 内部，直接跳过
  if (!activeEffect) return;

  // 2. 依次寻找或创建 targetMap -> depsMap -> dep 的层级结构
  let depsMap = targetMap.get(target);
  if (!depsMap) {
    depsMap = new Map();
    targetMap.set(target, depsMap);
  }

  let dep = depsMap.get(key);
  if (!dep) {
    dep = new Set();
    depsMap.set(key, dep);
  }

  // 3. 将当前活动副作用函数存入 dep 中
  trackEffects(dep);
}

/**
 * 具体的依赖添加逻辑（封装该方法，有利于后续重用，比如在 ref 的实现中）
 */
export function trackEffects(dep) {
  // 只有当 dep 里面还没有这个 activeEffect 时才添加（Set 本身去重，但这里做显式判断更安全）
  if (!dep.has(activeEffect)) {
    dep.add(activeEffect);
    
    // 🌟 核心铺垫：双向收集
    // 让 activeEffect 也记住它被收集到了哪些 dep 集合中。
    // 这将作为我们第四阶段实现“依赖清理（cleanup）”的基础。
    // 在最基础的 effectFn 上，我们需要挂载一个 deps 数组用来存储所有属于它的 dep
    if (activeEffect.deps) {
      activeEffect.deps.push(dep);
    }
  }
}
```

为了让 `activeEffect` 能够拥有 `.deps` 属性来支持双向收集，我们需要对上一节的 `effect` 函数进行微调：

```javascript
export function effect(fn) {
  const effectFn = () => {
    let lastEffect = activeEffect;
    try {
      activeEffect = effectFn;
      return fn();
    } finally {
      activeEffect = lastEffect;
    }
  };

  // 🌟 新增：初始化一个数组，用于保存所有包含当前 effectFn 的 dep 集合
  effectFn.deps = [];

  effectFn(); 
  return effectFn;
}
```

```javascript
import { track } from './reactive.js'; // 导入刚才写好的 track

const mutableHandlers = {
  get(target, key, receiver) {
    // 1. 执行真实的依赖收集
    track(target, key);

    // 2. 返回读取的值
    return Reflect.get(target, key, receiver);
  },
  
  set(target, key, value, receiver) {
    // （暂保持原样，下一节我们将在这里接入 trigger）
    const oldValue = target[key];
    const result = Reflect.set(target, key, value, receiver);
    if (oldValue !== value) {
      console.log(`[trigger 占位] 属性 "${key}" 被修改为: ${value}`);
    }

  }

```

### 3. 目前的依赖收集流程

现在，当代码执行如下逻辑时：
```javascript
effect(() => {
  console.log(state.count);
});
```

内部的流转步骤是：
1.  `effect(fn)` 执行。
2.  `effectFn` 将全局变量 `activeEffect` 标记为当前的自己，并且初始化 `effectFn.deps = []`。
3.  开始执行 `fn()`。
4.  代码读取 `state.count`，触发 Proxy 的 `get` 拦截。
5.  `get` 拦截器内部调用 `track(state, "count")`。
6.  `track` 顺着 `targetMap` 找到 `state` 对象对应的 `depsMap`，进而找到 `"count"` 属性对应的 `dep`（Set 集合）。
7.  把当前的 `activeEffect`（即 `effectFn`）放入该 `dep` 中；同时，在 `effectFn.deps` 中也塞入这个 `dep` [1]。
8.  完成双向绑定，数据读取成功。

现在，数据和函数之间已经成功地拉起了羁绊。

下一步，我们将进入 **第三阶段的第三部分：实现 trigger 函数（触发更新）**。当属性值发生改变时，我们需要通过 `trigger` 去主动通知并重新运行这些被收集在 `dep` 里的副作用。

## 实现 trigger 函数



在第三阶段的第三部分，我们将实现与 `track`（依赖收集）相辅相成的另一个核心函数 —— **`trigger`（触发更新）**。

`trigger` 的使命是：当某个响应式属性被修改时（触发 Proxy 的 `set`），顺着 `targetMap` 找到该属性对应的 `dep`（副作用函数集合），并**逐个重新执行**这些副作用函数，从而更新视图或计算属性。

---

### 1. 实现 `trigger` 函数

在实现 `trigger` 时，有两个经典的**细节坑**需要避开（这也是 Vue 3 源码中非常严谨的设计）：
1.  **避免 Set 死循环**：如果我们在遍历一个 `Set` 集合的同时，又往这个 `Set` 里添加元素（这在执行副作用时很常见），会导致 JavaScript 的 `forEach` 陷入无限循环。因此，在遍历执行前，我们需要**拷贝一份 `Set` 副本**。
2.  **避免无限递归（Self-triggering）**：如果副作用函数内部包含修改自身依赖数据的操作（例如 `effect(() => state.count++)`），这会同时触发 `get`（track）和 `set`（trigger）。如果不做限制，会导致该 `effect` 疯狂自我调用直到调用栈溢出。因此，我们应该**排除当前正在执行的 `activeEffect`**。

```javascript
import { activeEffect, targetMap } from './reactive.js'; // 确保路径正确

/**
 * 触发更新
 * @param {Object} target 原始目标对象
 * @param {string|symbol} key 被修改的属性名
 */
export function trigger(target, key) {
  // 1. 从 targetMap 中获取该对象的 depsMap
  const depsMap = targetMap.get(target);
  if (!depsMap) {
    // 如果该对象从未被收集过依赖，直接返回
    return;
  }

  // 2. 从 depsMap 中获取该属性对应的 dep (Set)
  const dep = depsMap.get(key);
  if (!dep) {
    // 如果该属性从未被收集过依赖，直接返回
    return;
  }

  // 3. 执行对应的副作用函数
  triggerEffects(dep);
}

/**
 * 具体的触发更新逻辑
 */
export function triggerEffects(dep) {
  // 坑 1 解决方案：创建 dep 的副本，避免直接遍历正在被修改的 Set 导致死循环
  const effectsToRun = new Set(dep);

  effectsToRun.forEach(effect => {
    // 坑 2 解决方案：如果触发更新的 effect 恰好是当前正在执行的 activeEffect，跳过它
    // 避免执行 state.count++ 这种操作时陷入无限递归
    if (effect !== activeEffect) {
      effect();
    }
  });
}
```

---

### 2. 更新 `reactive` 以接入真实的 `trigger`

现在，我们可以把 `reactive.js` 中的 `set` 拦截器彻底完善，用 `trigger` 替换之前的 `[trigger 占位]`。

```javascript
import { track, trigger } from './reactive.js'; // 导入 track 和 trigger

const mutableHandlers = {
  get(target, key, receiver) {
    track(target, key); // 依赖收集
    return Reflect.get(target, key, receiver);
  },
  
  set(target, key, value, receiver) {
    const oldValue = target[key];
    const result = Reflect.set(target, key, value, receiver);

    // 只有在值确实发生变化时，才触发更新
    if (oldValue !== value) {
      trigger(target, key); // 触发更新
    }
    return result;
  }
};
```

## 实现分支切换与依赖清理

在手写响应式系统的道路上，**“分支切换与依赖清理（Cleanup）”** 是一个区分普通开发者与资深开发者的关键分水岭。

这也是为什么我们在第三阶段的 `track` 实现中，坚持要做**双向收集**（让 `activeEffect` 也记住自己属于哪些 `dep`）的原因 [1]。

---

### 一、 条件分支导致的“残留依赖”痛点

我们通过一个经典的业务场景来分析：

```javascript
const state = reactive({ ok: true, text: 'hello' });

effect(() => {
  console.log('>>> effect 执行');
  document.body.innerText = state.ok ? state.text : 'alternative';
});
```

#### 1. 首次执行（`state.ok` 为 `true`）
*   由于 `state.ok` 是 `true`，三元运算符会去读取 `state.text`。
*   **收集到的依赖关系**：
    *   `state.ok` 对应的 `dep` 收集了该 `effect`。
    *   `state.text` 对应的 `dep` 也收集了该 `effect`。
    *   此时，`effect.deps` 记录了：`[ok的dep, text的dep]` [1]。

#### 2. 修改 `state.ok` 为 `false`
*   触发 `state.ok` 的更新，`effect` 重新运行。
*   在这次运行中，因为 `state.ok` 为 `false`，三元运算符直接返回 `'alternative'`，**根本没有去读取 `state.text`**。
*   此时按理说，`effect` 与 `state.text` 之间已经没有任何关系了。

#### 3. 产生残留依赖 Bug
*   如果我们尝试修改 `state.text = 'world'`。
*   由于我们之前没有进行清理，`state.text` 对应的 `dep` 集合中仍然残留着这个 `effect`。
*   结果：`state.text` 的修改依然会触发这个 `effect` 重新执行！
*   **这造成了不必要的性能开销，也就是“残留依赖”问题。**

---

### 二、 解决方案：在每次执行前进行 Cleanup

解决思路非常朴素且优雅：
> **每次副作用函数准备执行（或重新执行）之前，我们先把该副作用函数从所有依赖它的 `dep` 集合中删掉。执行时，让它顺着最新的代码逻辑重新收集一遍依赖。**

这样，当 `state.ok` 变成 `false` 重新执行时：
1.  执行前清空：把 `effect` 从 `ok` 和 `text` 的 `dep` 集合中移除。
2.  执行中重新收集：由于代码只读取了 `state.ok`，所以它只会被重新收集到 `ok` 的 `dep` 集合中。
3.  依赖关系更新完毕。此后再修改 `state.text`，就不会触发任何多余的执行。

---

### 三、 编写 `cleanup` 并重构 `effect`

#### 1. 实现 `cleanupEffect` 函数

```javascript
/**
 * 清理副作用函数关联的所有依赖集合
 * @param {Function} effectFn 包裹了用户函数的副作用执行函数
 */
function cleanupEffect(effectFn) {
  const { deps } = effectFn;
  if (deps.length) {
    for (let i = 0; i < deps.length; i++) {
      // deps[i] 是一个 dep（Set 集合）
      // 将当前的 effectFn 从该 Set 集合中移除
      deps[i].delete(effectFn);
    }
    // 清空完成，重置 effectFn 的 deps 数组
    deps.length = 0;
  }
}
```

#### 2. 重构 `effect` 函数
在执行用户传入的 `fn()` 之前，先调用 `cleanupEffect`：

```javascript
export let activeEffect = null;

export function effect(fn) {
  const effectFn = () => {
    let lastEffect = activeEffect;
    try {
      // 🌟 核心改动：在执行之前，先清除旧的依赖
      cleanupEffect(effectFn);
      
      activeEffect = effectFn;
      return fn(); // 执行过程中会触发全新的 track，重新收集当下真正用到的依赖
    } finally {
      activeEffect = lastEffect;
    }
  };

  // 初始化 deps 数组，用于双向收集
  effectFn.deps = [];

  effectFn(); 
  return effectFn;
}
```

---

### 四、 💡 精妙的呼应：为什么 trigger 中拷贝 Set 必不可少？

现在，我们能够更深刻地理解在上一节中，为什么 `trigger` 必须**创建副本**（`const effectsToRun = new Set(dep)`）了。

在 JavaScript 中，如果你在遍历一个 `Set` 的同时对其进行 `delete` 和 `add` 操作，会发生什么？
```javascript
// 如果 trigger 这样写：
dep.forEach(effect => effect()); 
```
1.  `trigger` 开始遍历 `dep` 集合，拿到 `effectFn` 并执行。
2.  `effectFn` 执行，首先调用 `cleanupEffect`，把自身从 `dep` 中 **`delete`** 掉。
3.  接着 `effectFn` 执行用户函数，触发 `track`，把自身重新 **`add`** 到 `dep` 中。
4.  根据 ECMAScript 规范，如果一个元素在 `forEach` 过程中被先删除再重新添加，遍历将再次访问该元素。
5.  **结果**：`forEach` 永远遍历不完，导致死循环（Call Stack Overflow）。

而在 `trigger` 中，我们使用了：
```javascript
const effectsToRun = new Set(dep); // 拷贝一个新 Set
effectsToRun.forEach(effect => effect());
```
我们遍历的是 `effectsToRun` 这个不会被修改的副本，而 `cleanup` 和 `track` 修改的是原始的 `dep`。两者互不干扰，从而完美、安全地避免了死循环。

### 五、 测试验证

我们可以编写一段测试代码，来验证依赖清理是否生效：

```javascript
import { reactive } from './reactive.js';
import { effect } from './effect.js';

const state = reactive({
  ok: true,
  text: 'hello'
});

// 记录 effect 执行的次数
let runCount = 0;

effect(() => {
  runCount++;
  console.log(`[Effect 运行第 ${runCount} 次] 展示文本: ${state.ok ? state.text : 'alternative'}`);
});

console.log('\n--- 1. 修改依赖中的 text 属性 ---');
state.text = 'world'; // 预期：会重新运行，触发更新
// 此时输出: [Effect 运行第 2 次] 展示文本: world

console.log('\n--- 2. 分支切换：修改 ok 属性为 false ---');
state.ok = false; // 预期：会重新运行，触发更新，并且在内部将 text 依赖清理掉
// 此时输出: [Effect 运行第 3 次] 展示文本: alternative

console.log('\n--- 3. 再次修改 text 属性 ---');
state.text = 'again'; 
// 💡 预期结果：控制台应该没有任何输出！因为此时 text 已经不再是该 effect 的依赖了！
console.log(`最终执行总次数: ${runCount}`); // 应该依然是 3 次
```

通过这套机制，Vue 3 能够做到对复杂逻辑分支变化时的依赖进行**极致动态精简**，确保没有一个多余的 `effect` 会因为过期数据而运行。
