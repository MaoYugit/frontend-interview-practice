## 支持嵌套对象的深度响应式

进入第四阶段，我们将对 `reactive` 进行完善。首要解决的问题，就是**支持嵌套对象的深度响应式**。

在 Vue 2 中，响应式是“**全量且一次性**”的：在初始化时，框架会通过递归强行遍历整张对象树，这在面对庞大或深层的数据结构时，会造成严重的启动卡顿和内存浪费。

而 Vue 3 利用 `Proxy` 的特性，巧妙地实现了一种 **“惰性代理（Lazy Proxy）”** 机制。

---

### 一、 什么是“惰性代理”？

当我们创建一个多层嵌套的响应式对象时：
```javascript
const state = reactive({
  user: {
    profile: {
      age: 18
    }
  }
});
```

*   **Vue 3 的处理方式**：在执行 `reactive` 时，它**只代理最外层对象**。此时，深层的 `user` 和 `profile` 还只是普通的普通对象，并没有被包装成 Proxy。
*   **什么时候代理深层？**
    只有当程序运行到某个地方，读取了 `state.user` 时（触发了最外层 Proxy 的 `get`），Vue 3 才会临时把 `{ profile: { age: 18 } }` 包装成一个 `reactive` 代理并返回。
*   **性能优势**：如果页面渲染自始至终都没有访问 `state.user.profile`，那么这个深层对象就永远不会被代理，这省去了大量无谓的初始化计算与内存占用。

---

### 二、 实现“惰性代理”

我们只需要对 `reactive.js` 中的 `mutableHandlers` 的 `get` 拦截器进行极简的改造：

```javascript
import { track } from './reactive.js';

// 辅助函数：判断是否为对象
function isObject(val) {
  return val !== null && typeof val === 'object';
}

const mutableHandlers = {
  get(target, key, receiver) {
    // 1. 进行依赖收集
    track(target, key);

    // 2. 获取当前的属性值
    const res = Reflect.get(target, key, receiver);

    // 🌟 核心改进：惰性代理
    // 如果获取到的值是对象，则递归调用 reactive 将其包装为 Proxy 后返回
    if (isObject(res)) {
      return reactive(res); // 此时用户拿到的就是一个深层的代理对象
    }

    return res;
  },

  set(target, key, value, receiver) {
    const oldValue = target[key];
    const result = Reflect.set(target, key, value, receiver);
    if (oldValue !== value) {
      trigger(target, key);
    }
    return result;
  }
};

export function reactive(target) {
  if (!isObject(target)) {
    return target;
  }
  return new Proxy(target, mutableHandlers);
}
```

### 三、 测试验证深度响应式

我们通过一段测试代码，来观察深度响应式和惰性代理的效果：

```javascript

    city: '北京'
  }
```

通过在 `get` 拦截器中进行简单的 `isObject(res) ? reactive(res) : res` 判断，我们用极小的代码成本，就达成了以下效果：
1.  **支持了任意深度的属性拦截**。
2.  **实现了“按需代理”**：只有真正被用到的深层数据才会被转化为 Proxy，大大提升了首屏加载性能。

## 处理边界情况

在第四阶段的第二部分，我们将处理手写响应式系统时非常关键的两个**边界情况**。这两个边界条件如果处理不当，会导致重复创建代理实例、浪费内存，甚至导致开发者在比对对象时产生不符合直觉的错误。

我们将采用与 Vue 3 源码一致的优雅方案来攻克它们。

---

### 一、 两个边界场景分析

#### 场景 1：重复代理同一个原始对象（Raw Object）
```javascript
const raw = { count: 1 };
const p1 = reactive(raw);
const p2 = reactive(raw);
console.log(p1 === p2); // 应该为 true！
```
*   **问题**：如果不做处理，每次调用 `reactive(raw)` 都会通过 `new Proxy` 产生一个崭新的代理实例，`p1` 和 `p2` 将指向不同的内存地址。这不仅浪费内存，还会破坏引用一致性。
*   **解决方案**：引入一个全局的缓存表 **`reactiveMap` (WeakMap)**。在创建代理前，先查表，如果发现已经为该原始对象创建过代理，则直接返回已有代理 [1]。

#### 场景 2：代理一个已经是 Proxy 的对象（Already a Proxy）
```javascript
const raw = { count: 1 };
const p1 = reactive(raw);
const p2 = reactive(p1); // 传入了代理对象 p1
console.log(p1 === p2); // 应该为 true！
```
*   **问题**：如果不做处理，`p2` 将会被再次包装为 `new Proxy(p1, ...)`，形成“Proxy 套 Proxy”的套娃现象，导致访问性能急剧下降。
*   **解决方案**：Vue 3 采用了一个非常精妙的设计 —— **“暗号标记”** [1]。
    *   定义一个特殊的 Key，例如 `"__v_isReactive"` [1, 2]。
    *   在 Proxy 的 `get` 拦截器中进行特殊判断：如果读取的属性是 `"__v_isReactive"`，直接返回 `true` [1, 2]。
    *   这样，当调用 `reactive(target)` 时，我们先去读取 `target.__v_isReactive` [1]。
    *   如果 `target` 是一个普通的非代理对象，读取该属性只会得到 `undefined`；而如果它已经是一个响应式 Proxy，则会触发它的 `get` 拦截，并直接返回 `true`！此时我们直接返回 `target` 本身即可 [1]。

---

### 二、 整合边界处理的代码实现

更新我们的 `reactive.js` 文件：

```javascript
import { track, trigger } from './reactive.js'; // 确保导入正常

// 辅助函数：判断是否为对象
function isObject(val) {
  return val !== null && typeof val === 'object';
}

// 定义一个特殊的标志，用来标识对象是否已经被代理
const IS_REACTIVE = '__v_isReactive';

// 🌟 针对场景 1：保存 原始对象 -> 代理对象 的缓存表
// 同样使用 WeakMap 防止内存泄漏
const reactiveMap = new WeakMap();

const mutableHandlers = {
  get(target, key, receiver) {
    // 🌟 针对场景 2：如果读取的 key 是我们的特殊标识，直接返回 true
    if (key === IS_REACTIVE) {
      return true;
    }

    track(target, key);

    const res = Reflect.get(target, key, receiver);

    // 惰性代理
    if (isObject(res)) {
      return reactive(res);
    }

    return res;
  },

  set(target, key, value, receiver) {
    const oldValue = target[key];
    const result = Reflect.set(target, key, value, receiver);
    if (oldValue !== value) {
      trigger(target, key);
    }
    return result;
  }
};

export function reactive(target) {
  // 如果不是对象，直接返回
  if (!isObject(target)) {
    return target;
  }

  // 🌟 针对场景 2：如果目标对象已经是响应式代理（访问特殊标识会返回 true），直接返回它
  if (target[IS_REACTIVE]) {
    return target;
  }

  // 🌟 针对场景 1：如果缓存表中已经存在该原始对象的代理，直接返回缓存的代理
  const existingProxy = reactiveMap.get(target);
  if (existingProxy) {
    return existingProxy;
  }

  // 第一次代理，正常创建
  const proxy = new Proxy(target, mutableHandlers);
  
  // 存入缓存表
  reactiveMap.set(target, proxy);

  return proxy;
}
```

## 实现调度器（Scheduler）

在 Vue 3 的响应式系统中，**调度器（Scheduler）** 是一项极为核心的设计。

它负责将“**何时执行副作用函数**”的控制权，从响应式系统的 `set/trigger` 内部，移交给外部（比如组件渲染、异步更新队列等）。这不仅是 Vue 实现**组件异步批量更新（nextTick）**的基础，也是后续实现 `computed` 和 `watch` 的基石。

下面我们一步步来实现一个功能完备的调度器，并基于它构建一个迷你版的“异步更新队列”。

---

### 一、 修改 `effect` 增加选项支持

目前我们的 `effect` 只接收一个参数 `fn`。现在我们需要对其进行重构，让它接收第二个可选参数 `options`，并将 `scheduler` 挂载到包装后的 `effectFn` 上。

更新 `effect.js`：

```javascript
export let activeEffect = null;

/**
 * 支持 options 参数的 effect
 * @param {Function} fn 
 * @param {Object} options 包含 scheduler 等选项
 */
export function effect(fn, options = {}) {
  const effectFn = () => {
    let lastEffect = activeEffect;
    try {
      cleanupEffect(effectFn);
      activeEffect = effectFn;
      return fn();
    } finally {
      activeEffect = lastEffect;
    }
  };

  effectFn.deps = [];
  
  // 🌟 将配置项挂载到 effectFn 上，以便 trigger 时能读取到
  effectFn.options = options;
  effectFn.scheduler = options.scheduler; // 快捷访问

  effectFn(); 
  return effectFn;
}

// 依赖清理逻辑保持不变...
function cleanupEffect(effectFn) {
  const { deps } = effectFn;
  if (deps.length) {
    for (let i = 0; i < deps.length; i++) {
      deps[i].delete(effectFn);
    }
    deps.length = 0;
  }
}
```

---

### 二、 重构 `trigger` 支持调度器

当触发更新时，如果发现副作用函数 `effect` 配置了 `scheduler`，我们应该**调用 `scheduler` 调度器，而不是直接执行 `effect()`**。

更新 `reactive.js` 中的 `triggerEffects` 方法：

```javascript
export function triggerEffects(dep) {
  const effectsToRun = new Set(dep);

  effectsToRun.forEach(effect => {
    if (effect !== activeEffect) {
      // 🌟 核心修改：如果存在调度器，执行调度器；否则默认直接执行副作用
      if (effect.scheduler) {
        effect.scheduler(); // 运行控制权移交给外部
      } else {
        effect(); // 默认同步执行
      }
    }
  });
}
```

---

### 三、 实战：利用 Promise 实现简易的异步批量更新（nextTick 雏形）

#### 1. 痛点场景分析
如果我们同步修改数据：
```javascript
state.count = 2;
state.count = 3;
state.count = 4;
```
如果不用调度器，上面的代码会触发 3 次 `trigger`，使得对应的 `effect` 同步执行 3 次。但在实际渲染中，我们只需要最后的最新值 `4`，前两次渲染属于严重的性能浪费。

#### 2. 实现一个异步任务队列（Job Queue）
我们可以利用 `Promise` 的微任务特性，实现一个异步队列，将多次数据的修改合并到同一个微任务中执行（即只执行最后一次更新）：

```javascript
// 存储待执行的副作用函数（使用 Set 自动去重）
const queue = new Set();
let isFlushing = false;
const resolvedPromise = Promise.resolve();

/**
 * 将任务加入队列，并在下一个微任务阶段统一清空
 */
export function queueJob(job) {
  // 1. 将任务加入去重的队列中
  queue.add(job);

  // 2. 如果队列还没有开始清空，则开启微任务清空逻辑
  if (!isFlushing) {
    isFlushing = true;

    // 3. 将清空队列的动作，放入微任务队列中（这就是 nextTick 的底层原理）
    resolvedPromise.then(() => {
      try {
        queue.forEach(job => job()); // 批量运行所有更新
      } finally {
        isFlushing = false;
        queue.clear(); // 运行完毕后清空任务队列
      }
    });
  }
}
```

### 四、 综合测试：调度器与异步批量更新

我们编写测试用例，来体验调度器的强大之处：

```javascript
import { reactive } from './reactive.js';
import { effect } from './effect.js';
import { queueJob } from './scheduler.js'; // 导入我们刚刚实现的任务队列

const state = reactive({ count: 1 });

// 1. 注册一个配置了 scheduler 的 effect
const effectFn = effect(() => {
  console.log(`[渲染更新] count 的值是: ${state.count}`);
}, {
  // 当 count 变化触发 trigger 时，Vue 3 不会立刻运行上面的 console.log
  // 而是会调用下面这个 scheduler 函数
  scheduler() {
    // 将副作用包裹函数放入我们的微任务批量队列中
    queueJob(effectFn);
  }
});

// 首次执行 effect，同步打印一次: [渲染更新] count 的值是: 1

console.log('\n--- 开始连续进行三次同步修改 ---');
state.count = 2;
state.count = 3;
state.count = 4;
console.log('--- 三次同步修改完成，主线程空闲 ---');

// 预期输出流程：
// 1. 首次打印: "[渲染更新] count 的值是: 1"
// 2. 打印 "--- 开始连续进行三次同步修改 ---"
// 3. state.count 变化 3 次，依次将 effectFn 添加到 queue 中（Set 自动去重，队列中其实只有一个任务）
// 4. 打印 "--- 三次同步修改完成，主线程空闲 ---"
// 5. 调用栈（Call Stack）清空，浏览器开始执行微任务队列（Promise.then）
// 6. 最终异步打印一次: "[渲染更新] count 的值是: 4"
```

### 总结

引入调度器后，我们的手写响应式系统已经具备了极高的灵活性：
1.  **控制权分离**：响应式系统只负责“通知数据变了”，至于“什么时候去更新”，交给调用方配置的 `scheduler` 去决定。
2.  **异步合并更新**：基于调度器与 Promise 微任务，我们成功复现了 Vue 3 的批量更新机制，避免了频繁触发视图渲染。

有了 `scheduler`，我们实际上已经扫清了实现 **第六阶段：实现 computed（计算属性）** 的最大障碍，因为计算属性的懒执行和缓存重置正是基于调度器实现的。
