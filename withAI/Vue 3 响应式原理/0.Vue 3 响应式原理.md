# 📚 Vue 3 响应式原理

### 第一阶段：基础准备（Proxy 与 Reflect）
*   **Vue 2 与 Vue 3 响应式实现方式的区别**：对比 `Object.defineProperty` 与 `Proxy` 的优缺点。
*   **Proxy 的基本用法**：拦截对象的 `get` 和 `set` 操作。
*   **为什么 Proxy 必须配合 Reflect 使用**：
    *   理解 `Reflect` 的基本 API。
    *   深入探讨 `this` 指向问题（通过 `receiver` 参数解决继承属性代理时的上下文偏离）。

### 第二阶段：核心概念与骨架（reactive 与 effect）
*   **实现最基础的 reactive 函数**：基于 `Proxy` 返回代理对象。
*   **理解 effect（副作用函数）**：
    *   实现一个最基础的 `effect` 函数。
    *   引入全局变量 `activeEffect`，用于记录当前正在执行的副作用函数。

### 第三阶段：依赖收集与触发（track 与 trigger）
*   **设计依赖管理的核心数据结构**：
    *   构建 `targetMap (WeakMap) -> depsMap (Map) -> dep (Set)` 的依赖关系树。
*   **实现 track 函数**：在 `get` 阶段收集当前 `activeEffect` 到对应的 `dep` 中。
*   **实现 trigger 函数**：在 `set` 阶段找到对应的 `dep`，并执行其中保存的所有副作用。
*   **🌟 进阶：实现分支切换与依赖清理（Cleanup）**：
    *   分析由于条件分支（三元运算符等）导致的残留依赖问题。
    *   通过在每次 `effect` 执行前清空其所在的依赖集合（`cleanupEffect`），并在执行时重新收集，解决该边界问题。

### 第四阶段：完善 reactive 与引入调度器（Scheduler）
*   **支持嵌套对象的深度响应式**：在 `get` 阶段进行惰性代理（Lazy Proxy）。
*   **处理边界情况**：
    *   利用 `reactiveMap`（WeakMap）防止重复代理同一个对象。
    *   防止代理已经是 Proxy 的对象。
*   **🌟 进阶：实现调度器（Scheduler）**：
    *   在 `effect` 选项中支持 `scheduler` 回调。
    *   修改 `trigger`：如果存在 `scheduler`，则执行 `scheduler` 而非直接运行副作用。
    *   （可选）利用微任务队列（Promise）实现一个简易的异步更新队列，理解 `nextTick` 的基本思路。

### 第五阶段：实现 ref
*   **为什么需要 ref**：理解 `reactive` 无法代理原始值（如数字、字符串）的原因。
*   **利用 Class 实现 ref**：
    *   利用 Class 的 `get value` 和 `set value` 拦截属性访问。
    *   在 getter 中调用 `trackEffects`，在 setter 中调用 `triggerEffects`。
*   **相关辅助函数**：实现 `isRef`、`unref`、`toRef` 与 `toRefs` 的基本逻辑。

### 第六阶段：🌟 进阶：实现 computed
*   **理解计算属性的特性**：懒执行（Lazy）与缓存机制。
*   **利用 effect 实现 computed**：
    *   为 `effect` 增加 `lazy` 配置项，允许不立即执行副作用。
    *   结合 `scheduler`，当依赖的响应式数据发生变化时，不直接重新计算，而是将缓存锁（`_dirty`）重置为 `true`。
    *   实现当计算属性被其他 effect 依赖时的“依赖收集”与“依赖触发”传递。

### 第七阶段：综合实战与验证
*   **代码整合**：将所有模块（reactive, ref, effect, computed）整合到同一个项目中。
*   **编写综合测试用例**：
    *   测试基本响应式更新。
    *   测试分支切换下的依赖清理。
    *   测试计算属性的缓存与更新。
*   **运行并调试**：通过控制台输出（`console.log`）观察依赖收集和触发的完整生命周期。

---

### 学习建议：
在动手编写时，可以采用 **“测试驱动”** 的思路。比如在写第三阶段前，先写一段包含分支切换的代码，看看它是否会产生 Bug，然后再引入 `cleanup` 逻辑去修复它。这样不仅能写出代码，还能更深刻地理解为什么要设计这些复杂的机制。
