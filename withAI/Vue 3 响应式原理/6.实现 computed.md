

## 理解计算属性的特性

在第六阶段，我们将攻克 Vue 3 中非常精妙、也是日常开发中使用高频的响应式 API —— **`computed`（计算属性）**。

在动手编写 `computed` 之前，我们需要通过深入剖析其两大王牌特性 —— **“懒执行（Lazy）”** 与 **“缓存机制”**，来理解它在底层是如何利用 `effect` 和 `scheduler` 运转的。

---

### 一、 特性 1：懒执行（Lazy）

传统的 `effect` 函数一旦被调用，其内部的副作用函数 `fn` 就会**立即执行一次**（为了触发首次 `get` 拦截进行依赖收集）。

然而，对于 `computed` 而言，这种立即执行往往是多余的：
```javascript
const fullName = computed(() => {
  console.log('计算属性执行了');
  return state.firstName + ' ' + state.lastName;
});
```
*   如果我们在模板或代码中**没有使用过** `fullName.value`，那么它的计算逻辑就永远不应该执行。
*   **设计思路**：`computed` 底层会利用一个特殊的 `effect`，但将配置项中的 `lazy` 设为 `true`。这意味着在创建该 `effect` 时，**跳过首次自动执行**，将执行时机推迟到用户真正访问 `.value` 的那一刻。

---

### 二、 特性 2：缓存机制（Caching）

计算属性最大的优势在于**缓存**。如果依赖的数据没有发生改变，连续访问 100 次计算属性，其内部的计算逻辑应该**只运行 1 次**。

#### 1. 核心设计：“脏状态标识（_dirty）”
为了控制缓存，我们需要在内部引入一个布尔值变量 `_dirty`（字面意思：脏的/需要更新的）：
*   **`_dirty === true`**：代表依赖的数据发生过变化，缓存失效了，**需要重新计算**。
*   **`_dirty === false`**：代表依赖的数据没变过，缓存依然有效，**直接返回上次的计算结果**。

#### 2. “缓存与重置”的闭环运转流程
这个“脏状态”在计算属性的整个生命周期中是这样流转的：

```text
【步骤 1：初始化】
创建 computed 实例 ──> 默认 _dirty = true

【步骤 2：首次读取】
读取 computed.value ──> 发现 _dirty 是 true ──> 运行计算函数 ──> 保存计算结果 ──> 将 _dirty 设为 false
                                                                                           │
【步骤 4：再次读取（依赖发生改变）】                                                          │
读取 computed.value ──> 发现 _dirty 是 true ──> 再次计算 ── <── 触发 scheduler 将 _dirty 设为 true 
                                                       （步骤 3：依赖的响应式数据改变）
```

*   **步骤 1：初始化**：`_dirty` 默认为 `true`。此时没有进行任何实际的计算。
*   **步骤 2：首次读取**：由于 `_dirty` 为 `true`，触发计算函数，计算出值并缓存起来。随后立即将 `_dirty` 设为 `false`。
*   **步骤 3：多次读取（数据没变）**：由于 `_dirty` 是 `false`，直接返回刚才缓存的值，绝不重复运行计算函数。
*   **步骤 4：依赖数据改变**：
    *   当计算属性所依赖的响应式数据（如 `state.firstName`）被修改时，会触发响应式系统的 `trigger`。
    *   但此时，`computed` **不会立刻去重新计算新值**。它会执行自己的 **`scheduler`（调度器）**。
    *   在 `scheduler` 内部，它只做一件事：**将 `_dirty` 重新重置为 `true`**。
*   **步骤 5：下一次读取**：当用户下一次读取 `computed.value` 时，由于 `_dirty` 在步骤 4 中被重置为了 `true`，它会再次运行计算函数，获取并缓存最新值，再次把 `_dirty` 设为 `false`。

---

### 三、 理论与前文的交汇点

你是否发现，`computed` 的缓存重置机制（步骤 4），完美契合了我们在第四阶段实现的 **调度器（Scheduler）**？
*   如果没有调度器，依赖项一变，副作用就会同步执行，我们根本没有机会在“数据变化后，重新计算前”将 `_dirty` 巧妙地设为 `true`。
*   有了调度器，我们就可以在调度器内部精准拦截：“**虽然依赖数据变了，但我现在不急着计算，我先把 _dirty 锁打开（置为 true），等用户下次需要的时候再算。**”

这种“按需计算”的高效模式，就是 Vue 3 计算属性的灵魂所在。

接下来，我们将进入 **第六阶段的第二部分：手写实现 Computed**。我们将结合 `lazy` 选项、`scheduler` 和刚才讨论的 `_dirty` 标识，把这个精妙的缓存系统用代码实现出来！

---

在这一部分，我们将融合前面实现的 `lazy` 选项、`scheduler`（调度器），并引入 `_dirty` 缓存锁，亲手实现 Vue 3 的核心功能之一 —— **`computed`（计算属性）**。

为了实现它，我们需要分为三步：修改 `effect` 支持懒执行、实现 `ComputedRefImpl` 缓存类、以及实现精妙的“依赖触发传递”。

---

### 第一步：修改 `effect` 支持 `lazy` 选项

我们需要确保如果配置了 `lazy: true`，`effect` 在初始化时**不要立刻执行**，而是将执行权交还给调用方。

更新 `effect.js`：

```javascript
export function effect(fn, options = {}) {
  const effectFn = () => {
    let lastEffect = activeEffect;
    try {
      cleanupEffect(effectFn);
      activeEffect = effectFn;
      return fn(); // 确保返回用户函数 fn() 的计算结果
    } finally {
      activeEffect = lastEffect;
    }
  };

  effectFn.deps = [];
  effectFn.options = options;
  effectFn.scheduler = options.scheduler;

  // 🌟 支持 lazy 配置：非 lazy 时才默认立即执行
  if (!options.lazy) {
    effectFn();
  }
  
  return effectFn; // 返回该包裹函数，供外部手动调用（例如 computed 手动执行）
}
```

### 第二步：手写实现 `computed`

新建一个 `computed.js`：

```javascript
import { effect, trackEffects, triggerEffects, activeEffect } from './effect.js';

class ComputedRefImpl {
  constructor(getter) {
    this._dirty = true;       // 缓存锁：默认为 true 代表需要重新计算
    this._value = undefined;  // 用于缓存计算出来的值
    this.dep = new Set();     // 🌟 专属依赖集：收集依赖这个计算属性的“外部 effect”
    this.__v_isRef = true;    // 标记计算属性本质上也是一个 Ref 引用

    // 1. 创建一个包裹 getter 的 lazy effect
    this.effect = effect(getter, {
      lazy: true,
      scheduler: () => {
        // 当计算属性所依赖的响应式数据改变时，触发此调度器
        if (!this._dirty) {
          this._dirty = true; // 1. 重置缓存锁为脏状态（需要重新计算）
          
          // 2. 🌟 依赖触发传递：通知所有依赖此计算属性的外部 effect 重新更新
          triggerEffects(this.dep);
        }
      }
    });
  }

  get value() {
    // 1. 🌟 依赖收集：如果当前有外部的 activeEffect 正在运行，把它收集到计算属性自己的 dep 中
    if (activeEffect) {
      trackEffects(this.dep);
    }

    // 2. 缓存控制
    if (this._dirty) {
      this._dirty = false;
      // 调用 effect() 执行用户传入的 getter，并缓存其计算返回值
      this._value = this.effect();
    }

    return this._value;
  }
}

/**
 * 创建计算属性
 * @param {Function} getter 计算属性函数 
 */
export function computed(getter) {
  return new ComputedRefImpl(getter);
}
```

### 三、 🌟 核心难点剖析：什么是“依赖触发传递”？

这是实现 `computed` 时最容易让人迷惑的地方：**为什么计算属性自身也要持有一个 `this.dep` 并进行依赖收集？**

我们通过下面这段业务代码的执行过程来进行推演：

```javascript
const state = reactive({ name: 'Bob' });
const upperName = computed(() => state.name.toUpperCase());

effect(() => {
  // 外部 effect 依赖了计算属性 upperName！
  console.log(`[DOM 更新] 名字变为: ${upperName.value}`);
});
```

#### 完整的依赖与触发传递流转链条：

1.  **外部 `effect` 首次执行**，其 `activeEffect` 被标记为 **“外部 effect”**。
2.  进入 `upperName.value` 的 `get`。
3.  发现存在 `activeEffect`（外部 effect），调用 `trackEffects(this.dep)`。
    *   **结果**：`upperName` 的 `dep` 集合中收集到了 **“外部 effect”**。
4.  由于 `_dirty` 是 `true`，`computed` 内部去执行它自己的 `this.effect()`（getter 的包裹函数）。
5.  在执行 `getter` 期间，`activeEffect` 被临时修改为了 **“computed 的内部 effect”**。
6.  `state.name` 被读取，触发 `reactive` 的 `get`。
    *   **结果**：`state.name` 的 `dep` 集合中收集到了 **“computed 的内部 effect”**。
7.  首次运行结束。
8.  **数据发生修改：`state.name = 'Alice'`**：
    *   触发 `state.name` 的 `trigger` ──> 运行 `computed 的内部 effect` 的调度器 `scheduler`。
    *   在 `scheduler` 中：
        1.  将 `_dirty` 设为 `true`。
        2.  **调用 `triggerEffects(this.dep)`**。因为步骤 3 中 `upperName.dep` 里存着 **“外部 effect”**，所以这一步会通知 **“外部 effect” 重新执行**。
    *   **外部 `effect` 重新执行**，再次读取 `fullName.value` ──> 发现 `_dirty` 是 `true` ──> 重新运行 `computed 的内部 effect` ──> 拿到最新值 `'ALICE'`。
    *   **更新完成！**

### 四、 综合测试验证

我们将所有特性连在一起进行测试，验证“懒执行”、“缓存机制”以及“依赖触发传递”是否完全吻合预期：

```javascript
import { reactive } from './reactive.js';
import { computed } from './computed.js';
import { effect } from './effect.js';

const state = reactive({
  firstName: '张',
  lastName: '三'
});

let computeCount = 0;

// 1. 定义计算属性
const fullName = computed(() => {
  computeCount++;
  return state.firstName + state.lastName;
});

// 💡 验证：懒执行。此时虽然定义了，但 computeCount 应该依然是 0
console.log('定义计算属性后，执行次数：', computeCount); // 预期：0

// 2. 外部 effect 依赖计算属性
effect(() => {
  console.log(`[DOM 模拟] 姓名是: ${fullName.value}`);
});
// 首次运行，打印: [DOM 模拟] 姓名是: 张三
console.log('首次读取后，执行次数：', computeCount); // 预期：1

// 3. 验证：缓存机制。连续读取 3 次，执行次数不应该增加
const t1 = fullName.value;
const t2 = fullName.value;
console.log('多次重复读取后，执行次数：', computeCount); // 预期：依然是 1！

console.log('\n--- 4. 修改 firstName ---');
state.firstName = '李'; 
// 预期：
// a. 触发 computed 的 scheduler ──> 触发外部 effect 重新执行
// b. 外部 effect 重新读取计算属性 ──> 发现 _dirty 是 true，重新计算 ──> 重新打印
// c. 打印出: [DOM 模拟] 姓名是: 李三
console.log('数据修改并重新渲染后，执行次数：', computeCount); // 预期：2
```
