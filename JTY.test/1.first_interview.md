### 1. 关于 HTTP 缓存，`Cache-Control: no-cache` 的含义是？

在 HTTP 缓存机制中，`Cache-Control: no-cache` 是一个经常被误解的指令。它的核心含义**并不是“不缓存”**，而是**“在使用缓存副本前，必须先向服务器确认其有效性”**。

以下是详细的解释：

1. 核心行为：强制重新验证 (Revalidation)

当你给一个响应设置了 `no-cache` 时，浏览器和中间代理服务器的操作流程如下：
1.  **存储缓存**：浏览器**会**把这个资源保存在本地缓存目录中。
2.  **请求拦截**：下次用户请求该资源时，浏览器不会直接从缓存中读取。
3.  **向服务器询问**：浏览器会向服务器发送一个“条件请求”（通常带有 `If-None-Match` 或 `If-Modified-Since` 头部）。
4.  **服务器判断**：
    *   如果资源**没变**：服务器返回 `304 Not Modified`。浏览器此时才放心使用本地的缓存副本。
    *   如果资源**变了**：服务器返回 `200 OK` 以及新的资源内容。浏览器更新缓存。

2. 它与 `no-store` 的区别（最易混淆点）

这是面试或开发中最常考的区别：
*   **`Cache-Control: no-cache`**：
    *   **会**缓存资源。
    *   但每次使用前**必须先去服务器验证**。
    *   目的：既想利用缓存减少数据传输（304响应非常小），又想保证获取的是最新内容。
*   **`Cache-Control: no-store`**：
    *   **完全不缓存**。
    *   浏览器不存，中间代理也不存。
    *   目的：用于处理高度敏感的数据（如银行账单），确保数据不在磁盘上留下痕迹。

3. 为什么不叫 "must-revalidate"？

其实 HTTP 协议中也有 `must-revalidate`，但它们的逻辑不同：
*   `max-age=60, must-revalidate`：在 60 秒内，可以**直接使用**缓存；超过 60 秒后，必须去服务器验证。
*   `no-cache`：等同于 `max-age=0, must-revalidate`。它要求**立即**验证，一秒钟的直接缓存时间都不给。

4. 使用场景

`no-cache` 非常适合以下场景：
*   **时效性要求高的动态内容**：比如新闻列表、天气预报、API 接口响应。你希望用户能用到缓存（节省流量），但绝对不能接受过时的信息。
*   **版本管理不便的资源**：如果你没法在 URL 中加入版本号（如 `script.js?v=1.2`），那么 `no-cache` 是保证用户总能拿到最新代码的安全手段。

5. 总结

| 指令 | 是否存入本地缓存 | 使用前是否咨询服务器 | 节省带宽的效果 |
| :--- | :--- | :--- | :--- |
| **`no-cache`** | 是 | **是** | 好（若资源未变，返回304，只传头部不传主体） |
| **`no-store`** | 否 | N/A (直接重新下载) | 无 |
| **`max-age=3600`** | 是 | 否（1小时内直接用） | 最好（连请求都不发） |

**一句话总结：**
`no-cache` 的真实意思是：**“可以缓存，但没得到服务器准许前，你不许偷用。”**

### 2. CSS预处理器有哪些？

CSS 预处理器（CSS Preprocessors）是为 CSS 增加一些编程特性的工具。它们允许你使用变量、嵌套、函数、混合（Mixins）等功能，然后将其编译成标准的 CSS 文件供浏览器读取。

目前市面上最主流的 CSS 预处理器有以下三种：

**1. Sass / SCSS (最流行)**

Sass 是目前前端开发中最常用、功能最强大的预处理器。
*   **两种语法**：
    *   **Sass (缩进语法)**：不使用花括号和分号，通过缩进来区分代码块（较老，类似 Python）。
    *   **SCSS (Sassy CSS)**：最常用的语法，完全兼容原生 CSS 语法（使用花括号和分号），学习成本极低。
*   **特点**：拥有极其强大的逻辑处理能力（`@if`, `@for`, `@each`）、混合器（Mixins）和广泛的社区支持。
*   **适用**：绝大多数现代前端项目（Vue, React 等）。

**2. Less**

Less 受 Sass 启发，但初衷是让 CSS 编写更简单。
*   **特点**：
    *   **语法亲和力**：语法与标准 CSS 非常接近。
    *   **运行环境**：Less 是由 JavaScript 编写的，因此除了在服务器端编译，还可以轻松地在浏览器端运行（虽然不推荐这样做）。
*   **成名原因**：早期大名鼎鼎的 UI 框架 **Bootstrap** (2.x 和 3.x 版本) 使用了 Less，这极大地推动了它的普及。
*   **现状**：虽然依然流行，但热度已被 Sass 超越。

**3. Stylus**

Stylus 诞生于 Node.js 社区，以“极简”和“灵活”著称。
*   **特点**：
    *   **语法极其自由**：你可以写括号，也可以不写；可以写冒号，也可以不写；可以写分号，也可以不写。
    *   **简洁性**：代码量通常是三者中最少的。
*   **现状**：在某些特定圈子（如极客或 Node.js 深度用户）中非常受欢，但相比 Sass 和 Less，社区规模稍小。

---

**核心功能对比（为什么要用它们？）**

无论你选择哪一种，它们通常都提供以下核心功能：

1.  **变量 (Variables)**：统一管理颜色、字体大小。
    *   `$primary-color: #333;` (Sass)
    *   `@primary-color: #333;` (Less)
2.  **嵌套 (Nesting)**：减少重复的选择器，让 CSS 结构清晰。
    ```scss
    nav {
      ul { margin: 0; }
      li { display: block; }
    }
    ```
3.  **混合 (Mixins)**：定义一段可重用的代码块，像调用函数一样使用。
4.  **计算 (Math)**：直接在 CSS 里写 `width: 100% - 20px;`。
5.  **模块化**：可以将样式拆分成多个小文件，最后编译成一个文件。

---

**特别补充：PostCSS (后处理器)**

虽然题目问的是“预处理器”，但现在不得不提 **PostCSS**。

*   **性质**：它不是严格意义上的预处理器，而是一个**插件系统**。
*   **功能**：通过不同的插件，它可以做到：
    *   **Autoprefixer**：自动补全浏览器私有前缀（-webkit-, -moz-）。
    *   **CSSNext**：让你现在就能使用未来的 CSS 新特性（将其转换为当前浏览器支持的语法）。
*   **现状**：现在很多开发者使用 **"Sass + PostCSS"** 的组合。

**总结：我该学哪个？**

*   如果你是**初学者**：推荐从 **SCSS** (Sass) 开始，因为它的工作机会最多，生态最完善。
*   如果你在使用某些**旧项目**：可能会遇到 **Less**（比如 Ant Design 早期版本）。
*   如果你追求**极致的代码简洁**：可以尝试 **Stylus**。

### 3. TypeScript 中，`interface` 和 `type` 的区别，描述错误的是？

A. interface 可以通过声明合并（Declaration Merging）自动扩展
B. type 可以使用 computed properties，interface 不行 正确答案
C. type 可以定义联合类型，interface 不行
D. 官方推荐在大多数情况下优先使用 interface

这道题的正确答案是 **B**。

在 TypeScript 中，描述错误的是 **B：type 可以使用 computed properties，interface 不行**。

以下是针对各选项的详细解析：

**A. interface 可以通过声明合并（Declaration Merging）自动扩展（描述正确）**

这是 `interface` 的一个核心特性。如果你定义了两个同名的 `interface`，TypeScript 会自动将它们合并为一个。
```typescript
interface User { name: string; }
interface User { age: number; }

// 结果 User 同时拥有 name 和 age
const user: User = { name: "Tom", age: 18 }; 
```
而 `type` 不支持声明合并，同名定义会报错。

**B. type 可以使用 computed properties，interface 不行（描述错误 —— 本题答案）**

**错误原因**：实际上，**`interface` 和 `type` 都可以使用计算属性（Computed Properties）**。
```typescript
const propName = "dynamicKey";

// type 支持
type T = { [propName]: string };

// interface 也支持
interface I { [propName]: string };
```
*注：可能导致混淆的点是 **映射类型（Mapped Types）**。`type` 可以使用映射类型（如 `type Keys = 'a'|'b'; type Obj = { [K in Keys]: string }`），而 `interface` 确实不支持映射类型。但“计算属性”不等同于“映射类型”。*

**C. type 可以定义联合类型，interface 不行（描述正确）**

`type`（类型别名）可以指向任何类型，包括原始类型、联合类型、元组等。
```typescript
type MyType = string | number; // 联合类型
type Data = [number, string];  // 元组
```
`interface` 只能用于定义**对象结构**，无法直接定义联合类型或基本类型。

**D. 官方推荐在大多数情况下优先使用 interface（描述正确）**

TypeScript 官方文档建议：
1.  **优先使用 `interface`**：因为 `interface` 的性能通常比 `type` 稍微好一点（编译器缓存），并且它支持声明合并，这对开发第三方库非常友好（允许用户扩展你的类型）。
2.  **当需要 `interface` 无法实现的功能时再使用 `type`**：例如需要联合类型、元组、映射类型或处理基本类型时。

---

### 总结对比表

| 特性 | interface | type |
| :--- | :--- | :--- |
| **定义类型范围** | 仅限于对象/函数结构 | 任何类型（原始、联合、元组等） |
| **声明合并** | 支持 | 不支持 |
| **继承方式** | `extends` | `&` (交叉类型) |
| **计算属性** | **支持** | **支持** |
| **映射类型** | 不支持 | 支持 |
| **报错信息展示** | 较清晰（通常显示接口名） | 有时会直接展开复杂结构 |

### 4. TypeScript中，interface和type的主要区别不包括？

A. type性能更好 
B. interface可以合并
C. interface可以继承
D. type可以定义联合类型

这道题的正确答案是 **A**。

以下是详细解析：

**A. type 性能更好（错误，这不是主要区别）**

*   **解析**：这不仅不是它们的主要区别，甚至在某些情况下，**`interface` 的性能反而优于 `type`**。
*   **原因**：TypeScript 编译器在处理 `interface` 时会建立一个扁平的缓存结构，当进行类型合并或继承检查时，这种缓存能让性能更好。而 `type`（特别是包含交叉类型 `&` 的复杂类型）在编译器中需要进行更多的递归计算。
*   **结论**：在实际开发中，这点性能差异对普通项目几乎无感，但官方确实建议为了编译器性能，能用 `interface` 时优先用 `interface`。

---

**B. interface 可以合并（正确，是主要区别）**

*   **解析**：这是 `interface` 特有的**声明合并（Declaration Merging）**功能。
*   **示例**：
    ```typescript
    interface User { name: string; }
    interface User { age: number; }
    // 自动合并为 { name: string, age: number }
    ```
*   `type` 不允许重复定义同名类型，否则会报错。

---

**C. interface 可以继承（正确，是主要区别）**

*   **解析**：虽然两者都能实现类似的扩展功能，但方式不同。
*   **`interface`**：使用显式的 `extends` 关键字（如 `interface Student extends Person`）。
*   **`type`**：通过交叉类型 `&` 来模拟“继承”（如 `type Student = Person & { grade: number }`）。

---

**D. type 可以定义联合类型（正确，是主要区别）**

*   **解析**：这是 `type` 的强大之处，它可以定义 `interface` 无法表达的非对象类型。
*   **示例**：
    ```typescript
    type Status = "success" | "error" | "loading"; // 联合类型
    type Data = string | number;                  // 基本类型的组合
    ```
*   `interface` 只能用来描述对象的形状（Object Shape），不能直接定义联合类型。

---

**总结**

这道题考察的是对 TypeScript 官方推荐实践的理解。**B、C、D 都是语法功能上的核心区别**，而 **A 则是一个错误的性能误区**。官方文档（Performance 章节）明确指出：
> *“Interfaces describe a single flat object type ... whereas type aliases can be used for any type. Because an interface has a specific shape, it’s easier for TypeScript to cache and perform lookups.”* 
> （接口描述单一的扁平对象类型...因此更容易缓存和查询。）

### 5. HTTP/2相比HTTP/1.1有哪些改进？

A. 多路复用
B. 文本协议 
C. 服务器推送
D. 头部压缩

这道题的正确答案是 **A、C、D**。

HTTP/2 是对 HTTP/1.1 的一次重大升级，旨在提高性能和效率。以下是各选项的详细解析：

**A. 多路复用 (Multiplexing) —— 正确**

*   **HTTP/1.1 的问题**：浏览器对同一个域名的并行 TCP 连接数有限制（通常为 6 个），且存在“队头阻塞”（Head-of-Line Blocking）问题，一个请求如果卡住了，后续请求都得等。
*   **HTTP/2 的改进**：允许在**同一个 TCP 连接**上同时发送多个请求和响应。数据被分成独立的“帧”，交错传输，互不干扰，彻底解决了 HTTP 层的队头阻塞。

**B. 文本协议 —— 错误**

*   **事实**：HTTP/1.1 是文本协议（你可以直接阅读原始报文）。
*   **HTTP/2 的改进**：HTTP/2 采用了**二进制分帧（Binary Framing）**。它不再是文本格式，而是将所有信息封装在更小的二进制帧中。二进制格式解析速度更快、更紧凑，且错误率更低。

**C. 服务器推送 (Server Push) —— 正确**

*   **HTTP/1.1 的行为**：只有客户端请求了，服务器才会返回。
*   **HTTP/2 的改进**：服务器可以“预测”客户端需要什么。比如当客户端请求 `index.html` 时，服务器可以主动把配套的 `style.css` 和 `main.js` 推送到客户端的缓存中，减少了往返时延（RTT）。

**D. 头部压缩 (Header Compression) —— 正确**

*   **HTTP/1.1 的问题**：HTTP 头部（Headers）通常包含大量重复信息（如 User-Agent、Cookie 等），且全是文本，浪费带宽。
*   **HTTP/2 的改进**：使用了 **HPACK 算法**。客户端和服务器共同维护一张头部哈希表，重复的头部不再发送，只发送索引号。这对于有大量小请求（如大量小图标）的场景能显著减少流量。

---

**总结 HTTP/2 的四大核心特性：**

1.  **二进制分帧**（Binary Framing）：协议的基础，取代了文本协议。
2.  **多路复用**（Multiplexing）：解决队头阻塞，提升并发能力。
3.  **头部压缩**（HPACK）：减少冗余数据。
4.  **服务器推送**（Server Push）：优化资源加载顺序。

### 6. React 中，`useEffect` 的第二个参数如果是空数组 `[]`，其效果等同于哪个生命周期钩子？

A. componentDidUpdate
B. componentDidMount 
C. shouldComponentUpdate 
D. componentWillUnmount

这道题的正确答案是 **B**。

以下是详细解析：

**1. 为什么是 `componentDidMount`？**

在 React 类组件中，`componentDidMount` 会在组件挂载到 DOM 后**仅执行一次**。

而在函数组件中，`useEffect` 的行为由第二个参数（依赖数组）决定：
*   **不传第二个参数**：每次渲染后都会执行。
*   **传空数组 `[]`**：告诉 React 这个 Effect **不依赖于**组件中的任何值（props 或 state）。因此，它**只会在组件挂载（Mount）时执行一次**，之后无论组件如何更新，它都不会再次运行。
*   **这种“只在挂载时运行一次”的行为，在逻辑上完全对应 `componentDidMount`。**

**2. 为什么候选人选择的 C (`shouldComponentUpdate`) 是错的？**

*   **`shouldComponentUpdate` 的作用**：它是一个性能优化钩子，用来决定组件**是否需要**重新渲染（返回 `true` 或 `false`）。
*   **`useEffect` 的作用**：它是用来处理**副作用**的（如发送请求、操作 DOM、订阅事件），它发生在渲染**之后**。
*   **对应关系**：在函数组件中，对应 `shouldComponentUpdate` 功能的通常是 **`React.memo`** 或 **`useMemo`**，而不是 `useEffect`。

**3. 其他选项解析**

*   **A. `componentDidUpdate`**：
    这是在组件**更新**后执行的。如果你不给 `useEffect` 传第二个参数，或者在依赖数组里填了某些变量（如 `[count]`），那么它的行为就包含（但不等同于）`componentDidUpdate`。
*   **D. `componentWillUnmount`**：
    这是在组件**销毁**前执行的。在 `useEffect` 中，如果你**返回一个函数**（Cleanup 函数），那么这个返回的函数在组件卸载时的行为等同于 `componentWillUnmount`。
    ```javascript
    useEffect(() => {
      // 这里相当于 componentDidMount
      return () => {
        // 这里才相当于 componentWillUnmount
      };
    }, []);
    ```

### 总结
| `useEffect` 形式                            | 对应的类组件生命周期                       |
| :------------------------------------------ | :----------------------------------------- |
| `useEffect(() => { ... }, [])`              | **`componentDidMount`**                    |
| `useEffect(() => { ... })`                  | `componentDidMount` + `componentDidUpdate` |
| `useEffect(() => { return () => ... }, [])` | `componentWillUnmount`                     |

### 7.**请使用JavaScript实现一个发布-订阅模式（EventEmitter），包含on、emit、off方法。**

```js
class EventEmitter {
  constructor() {
    // 使用 Object.create(null) 创建一个纯净的对象，用于存储事件和回调
    // 键是事件名，值是回调函数数组：{ "event1": [cb1, cb2], "event2": [cb3] }
    this._events = Object.create(null);
  }

  /**
   * 订阅事件
   * @param {string} eventName 事件名称
   * @param {Function} callback 回调函数
   */
  on(eventName, callback) {
    if (!this._events[eventName]) {
      // 如果第一次订阅该事件，初始化数组
      this._events[eventName] = [];
    }
    this._events[eventName].push(callback);
  }

  /**
   * 发布事件
   * @param {string} eventName 事件名称
   * @param {...any} args 传递给回调的参数
   */
  emit(eventName, ...args) {
    const callbacks = this._events[eventName];
    if (callbacks) {
      // 循环执行该事件下的所有回调
      callbacks.forEach(cb => {
        cb(...args);
      });
    }
  }

  /**
   * 取消订阅
   * @param {string} eventName 事件名称
   * @param {Function} callback 要移除的特定回调
   */
  off(eventName, callback) {
    const callbacks = this._events[eventName];
    if (callbacks) {
      // 过滤掉匹配的回调函数
      this._events[eventName] = callbacks.filter(cb => cb !== callback);
    }
    
    // 如果该事件下没有回调了，建议删除键值对释放内存
    if (this._events[eventName]?.length === 0) {
      delete this._events[eventName];
    }
  }

  /**
   * 只订阅一次（补充常用方法）
   */
  once(eventName, callback) {
    // 创建一个包裹函数，执行完立即销毁自身
    const wrapper = (...args) => {
      callback(...args);
      this.off(eventName, wrapper);
    };
    this.on(eventName, wrapper);
  }
}

// --- 测试代码 ---

const bus = new EventEmitter();

// 1. 测试 on 和 emit
const handleWelcome = (name) => console.log(`Hello, ${name}!`);
bus.on('welcome', handleWelcome);
bus.emit('welcome', 'Alice'); // 输出: Hello, Alice!

// 2. 测试多个监听者
bus.on('welcome', (name) => console.log(`${name} joined the chat.`));
bus.emit('welcome', 'Bob'); 
// 输出: 
// Hello, Bob!
// Bob joined the chat.

// 3. 测试 off
bus.off('welcome', handleWelcome);
bus.emit('welcome', 'Charlie');
// 只输出: Charlie joined the chat. (handleWelcome 已被移除)

// 4. 测试 once
bus.once('gift', (item) => console.log(`Got a ${item}!`));
bus.emit('gift', 'Apple'); // 输出: Got a Apple!
bus.emit('gift', 'Apple'); // 无输出（已自动销毁）
```

### 8.**在 Web 性能优化中，'关键渲染路径'（Critical Rendering Path）不包括以下哪个步骤？**

A. 执行 JavaScript

B. 建立 TCP 连接 

C. 构建 CSSOM 树

D. 构建 DOM 树

这道题的正确答案是 **B**。

**详细解析：**

**关键渲染路径（Critical Rendering Path, CRP）** 指的是浏览器从收到 HTML、CSS 和 JavaScript 字节开始，到将其转换为屏幕上像素的过程。

**1. 为什么 B（建立 TCP 连接）不属于 CRP？**

*   **阶段不同**：建立 TCP 连接属于**网络传输阶段**（Loading/Networking）。它发生在浏览器发送 HTTP 请求之前。
*   **CRP 的起点**：关键渲染路径通常是从浏览器**接收到 HTML 数据**的那一刻开始算的。
*   **职责不同**：TCP、DNS 解析、TLS 握手等属于“如何把资源拿回来”，而 CRP 属于“拿到资源后如何渲染出来”。

---

**2. 关键渲染路径（CRP）包含的 5/6 个核心步骤：**

选项 A、C、D 都在这套流程中：

1.  **构建 DOM 树 (D 选项)**：
    浏览器解析 HTML 字节，转换成字符、令牌、节点，最终构建成 Document Object Model (DOM)。
2.  **构建 CSSOM 树 (C 选项)**：
    浏览器解析 CSS 文件或内联样式，构建出 CSS Object Model (CSSOM)。
3.  **执行 JavaScript (A 选项)**：
    JavaScript 可以修改 DOM 和 CSSOM。由于 JS 可能会改变页面结构，它会**阻塞** DOM 的构建（除非使用 `defer` 或 `async`），因此它是路径中至关重要的一环。
4.  **合并渲染树 (Render Tree)**：
    将 DOM 和 CSSOM 合并，生成渲染树（只包含可见的节点，比如 `display: none` 的节点不会出现在这里）。
5.  **布局 (Layout/Reflow)**：
    计算每个可见节点在屏幕上的确切位置和大小。
6.  **绘制 (Paint)**：
    将渲染树中的每个节点转换成屏幕上的实际像素。

---

**总结**

*   **网络层**（DNS, TCP, HTTP 请求）：负责获取数据。
*   **关键渲染路径 (CRP)**：负责处理数据并显示图像。

所以，**建立 TCP 连接** 是性能优化的重要环节（影响白屏时间），但在技术定义上，它不属于“渲染路径”的一部分。
